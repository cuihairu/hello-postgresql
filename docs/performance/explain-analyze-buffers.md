# EXPLAIN (ANALYZE, BUFFERS, WAL)

Plain `EXPLAIN` gives estimates only; add `ANALYZE` and the statement really runs once, so every node in the plan gets an actual time, actual row count, and execution count; add `BUFFERS` and you can see how many blocks each node read, how many came from cache and how many spilled to temp files; `WAL` (PG 13+) additionally counts the log volume generated by write statements. This page gathers how to use that combination, a field-by-field reading of the output, and two frequent misreadings: loops multiplication and temp files.

## ANALYZE Really Executes: Wrap Writes in a Transaction and Roll Back

`EXPLAIN (ANALYZE)` performs a complete execution of the statement (the result set is discarded, not returned to the client), so UPDATE/DELETE/INSERT really change data, triggers really fire, and all side effects take hold. When tuning write statements, wrap them in a transaction and roll back:

```sql
BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
UPDATE orders SET status = 'paid' WHERE order_id = 12345;
ROLLBACK;   -- data is restored, but the execution fully happened once
```

Three caveats: the rollback itself also produces WAL and dead tuples, so do not run this casually on a busy primary; for non-transactional side effects such as sequence nextval, a rollback cannot undo them; and statements containing `SELECT pg_sleep(...)` or large DML need a serious estimate of execution time so you do not lock business rows.

## A Complete Sample: Reading It Line by Line

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT user_id, sum(amount)
FROM orders
WHERE created_at >= now() - interval '7 days'
GROUP BY user_id
ORDER BY sum(amount) DESC
LIMIT 20;
```

```plaintext
Limit (cost=20834.71..20834.76 rows=20 width=40) (actual time=41.219..41.226 rows=20 loops=1)
  Buffers: shared hit=5403
  ->  Sort (cost=20834.71..20860.82 rows=10443 width=40) (actual time=41.216..41.222 rows=20 loops=1)
        Sort Key: (sum(amount)) DESC
        Sort Method: top-N heapsort  Memory: 27kB
        Buffers: shared hit=5403
        ->  HashAggregate (cost=19727.50..19797.13 rows=10443 width=40) (actual time=38.910..40.501 rows=8932 loops=1)
              Group Key: user_id
              Batches: 1  Memory Usage: 1281kB
              Buffers: shared hit=5403
              ->  Seq Scan on orders
                    (cost=0.00..19144.58 rows=116583 width=14)
                    (actual time=0.011..20.555 rows=77778 loops=1)
                    Filter: (created_at >= (now() - '7 days'::interval))
                    Rows Removed by Filter: 922222
                    Buffers: shared hit=5403
Planning:
  Buffers: shared hit=36
Planning Time: 0.180 ms
Execution Time: 41.310 ms
```

Reading it line by line:

- **Seq Scan node**: the data source. Estimated 116583 rows, actual 77778—same order of magnitude, so the estimate is trustworthy; `Rows Removed by Filter: 922222` says 92% of the million rows in the table were filtered out—if this is a high-frequency query, that is direct evidence it "deserves an index".
- **HashAggregate node**: groups by `user_id`. `Batches: 1` means the hash table fit in work_mem in one pass (>1 means the grouping spilled to disk); `Memory Usage: 1281kB` is the actual occupancy.
- **Sort node**: sorts the aggregate result descending. `Sort Method: top-N heapsort` is the optimization triggered by LIMIT 20—maintaining a small min-heap of 20 rows instead of sorting everything; without a LIMIT you would see `quicksort Memory: xxx` (in-memory sort) or `external merge Disk: xxx` (spilled to disk).
- **Buffers on each node**: the whole path is shared hit=5403, entirely cache hits with zero disk reads, which means the time went into CPU filtering and aggregation rather than IO.
- **Planning** section (shown by default since PG 13): planning itself read 36 cached blocks, and `Planning Time` of 0.18 ms is negligible; if a complex query takes hundreds of milliseconds just to plan, the problem is in planning, not execution.
- **Execution Time**: excludes network transfer and the time the client spends fetching data.

## actual time and loops: the Multiplication Trap

The ANALYZE output triple is `(actual time=startup..total rows=N loops=K)`: time is in milliseconds, rows is the average number of rows this node outputs **per loop**, and loops is how many times the node ran in total. Nodes driven repeatedly by an upper node (the inner side of a Nested Loop, say) have loops far above 1, in which case:

- **total time ≈ actual time × loops**—looking at time alone underestimates by orders of magnitude;
- **total rows = rows × loops**—rows showing as a fraction is normal (it is an average).

```plaintext
Nested Loop (cost=0.42..89.70 rows=10 width=16)
            (actual time=0.040..852.411 rows=100000 loops=1)
  ->  Index Scan using users_pkey on users u
        (cost=0.42..8.44 rows=1 width=8) (actual time=0.030..50.203 rows=10000 loops=1)
        Index Cond: (user_id < 10001)
  ->  Index Scan using orders_user_id_idx on orders o
        (cost=0.00..8.12 rows=10 width=8)
        (actual time=0.001..0.080 rows=10.0 loops=10000)
        Index Cond: (user_id = u.user_id)
```

The inner index scan `actual time=0.001..0.080` looks like just 0.08 milliseconds, but loops=10000, so it actually contributes about 800 milliseconds—that is the classic "see 0.0x ms and assume it is fast" trap. Likewise, rows=10.0 × 10000 loops = 100,000 rows. When judging a bad node, always convert "time × loops" and "rows × loops" to totals before comparing.

## Buffers: Hits, Reads and Temp Files

`BUFFERS` accounts for each node's IO in blocks (default 8kB):

- **shared hit**: hit in shared_buffers, a pure in-memory operation;
- **shared read**: not in cache, read from storage (it may have been served by the OS file cache, so this does not necessarily mean a real disk hit);
- **shared dirtied / written**: blocks dirtied and flushed out, common for write statements;
- **temp read / written**: **temp file reads/writes**—their appearance means sort/hash data exceeded work_mem, the most direct "out of memory" signal.

Diagnostic routine: low `hit` share → cache is small or data is cold, consider enlarging `shared_buffers` or checking whether you are doing full table scans; large `temp written` → tune `work_mem`, or eliminate the sort with an index; a single node owning most of the buffers → it is your IO hotspot. The principles behind continuously observing per-instance statistics are covered in [Observing Statistics](../internals/pg-stat-observation).

## WAL Accounting (PG 13+)

The `WAL` option only applies to nodes that generate log records, and is commonly used to assess write amplification:

```sql
BEGIN;
EXPLAIN (ANALYZE, WAL)
UPDATE orders SET status = 'paid' WHERE order_id = 12345;
ROLLBACK;
```

```plaintext
Update on orders (actual time=0.512..0.514 rows=1 loops=1)
  ->  Index Scan using orders_pkey on orders
        (actual time=0.038..0.040 rows=1 loops=1)
        Index Cond: (order_id = 12345)
        WAL: records=4 bytes=1000 fpi=1
Query Identifier: 1873462406727496351
Planning Time: 0.145 ms
Execution Time: 0.633 ms
```

`records` is the number of WAL records, `bytes` the byte count, and `fpi` the number of full page images (written when a page is modified for the first time after a checkpoint, copying the whole page). A large fpi means you caught the first wave of writes after a checkpoint—that is normal, but watch checkpoint frequency, see [Checkpoints and Buffers](../internals/checkpoint-and-buffer). The WAL bytes of bulk write statements also help you estimate replication lag and archival pressure.

## Timing Overhead and the cost/actual Comparison

`ANALYZE` defaults to `TIMING ON`, so every node reads the clock; for queries producing enormous row counts, the cost of timing itself can eat a significant share (more pronounced in older versions). When you only care about row counts and buffers, turn it off:

```sql
EXPLAIN (ANALYZE, TIMING OFF, BUFFERS) SELECT ...;  -- still gives per-node rows and total execution time
```

Also note that cost and actual are two separate systems: cost is a pricing derived from statistics (see [Optimizer Cost Model](../internals/optimizer-cost-model)), actual is measured. Comparing them is not about converting between the two, but about finding nodes "the optimizer thought were cheap, that are actually expensive"—that is exactly where estimation is distorting.

## Caveats and Common Pitfalls

- `EXPLAIN (ANALYZE)` executes fully and then discards the result set, but scans, functions and triggers really happen; always wrap DML in a transaction and roll back.
- `actual time` and `rows` are per-loop averages; multiply by loops before comparing node costs.
- Buffer accounting has some overlap error; summing across nodes is not guaranteed to equal the top-level value exactly.
- Results depend heavily on cache warmth: run once on a cold cache, once on a warm cache, and the conclusions can be opposite; for important conclusions run several times and take the stable value.
- Statistics are sampled at the moment of execution; the average in `rows` means that under an extremely skewed distribution a single loop's row count can differ wildly.
- `BUFFERS` only includes planning-phase buffer accounting from PG 13 onward; older version output has no Planning section.
