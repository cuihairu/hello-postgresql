# Schema Migration Tools

Running `CREATE TABLE` locally once is easy. The hard part is making the schema on dozens of environments (dev, test, staging, multiple production nodes, every developer's machine) **evolve consistently**. Migration tools exist to solve exactly that.

## The three problems migrations solve

- **Replayable**: any brand-new environment can run all migration files in order and end up with the same current structure as production;
- **Rollback-capable**: when a release goes wrong you have to be able to step back to the previous version, so every change ideally has a corresponding reverse operation;
- **Accountable**: who changed what in which version — files, records, reviewable.

All mainstream tools revolve around "**an ordered set of versioned SQL files plus a table recording the current version**." The differences are only in file naming, metadata management, and surrounding ecosystem.

## golang-migrate

A migration is a pair of files: `up` moves forward, `down` rolls back, and file names start with a six-digit sequence number:

```plaintext
migrations/
  000001_create_users.up.sql
  000001_create_users.down.sql
  000002_add_orders_status.up.sql
  000002_add_orders_status.down.sql
```

```bash
# Generate an empty pair of files
migrate create -ext sql -dir migrations -seq add_orders_status

# Execute and roll back (the connection string must carry parameters like sslmode)
migrate -path migrations -database "postgres://app:secret@localhost:5432/appdb?sslmode=disable" up 1
migrate -path migrations -database "postgres://app:secret@localhost:5432/appdb?sslmode=disable" down 1

# Migrate to a specific version / show the current version
migrate -path migrations -database "$DB_URL" goto 000002
migrate -path migrations -database "$DB_URL" version
```

Applied versions are recorded in the `schema_migrations` table. One mechanism worth knowing is the **dirty flag**: when a migration fails mid-execution, that version gets marked dirty, and the next run refuses to continue. You have to confirm manually and clear it with `force` before going on — better to stop and ask a human than to let a half-finished structure keep propagating.

## Flyway

Flyway distinguishes types by name prefix. `V` is a versioned migration, and `R` is repeatable (objects like views and functions that should "always be aligned to the latest definition"):

```plaintext
db/migration/
  V1__create_users.sql
  V2__add_orders_status.sql
  R__current_order_view.sql
```

```bash
# When bringing an existing database with a pre-existing structure under Flyway, create a baseline first
flyway -url=jdbc:postgresql://localhost:5432/appdb -user=app baseline -baselineVersion=1
flyway -url=jdbc:postgresql://localhost:5432/appdb -user=app migrate
flyway -url=jdbc:postgresql://localhost:5432/appdb -user=app info
```

The point of `baseline`: an existing database is effectively already at V1, so a plain `migrate` errors out because V1 conflicts with the current state. Once you set the baseline, Flyway starts applying from V2. Execution records live in the `flyway_schema_history` table.

## prisma migrate

Prisma flips the approach: **the `schema.prisma` file is the single source of truth**, and SQL is generated by the tool comparing definitions:

```bash
# After editing schema.prisma, compare to generate migration SQL and apply it to the dev database
npx prisma migrate dev --name add_orders_status

# In production, only apply already-generated migrations — no diffing or generation
npx prisma migrate deploy

# Bringing an existing database in: mark the already-existing initial migration as applied
npx prisma migrate resolve --applied 20240101120000_init
```

The SQL generated by `migrate dev` lives at `prisma/migrations/<timestamp>_<name>/migration.sql` and, like the other tools, goes into version control for review. A good fit for teams already using the Prisma ORM; pure-SQL teams are more directly served by golang-migrate or Flyway.

The Node ecosystem also has [node-pg-migrate](https://github.com/salsita/node-pg-migrate), which isn't tied to an ORM and writes up/down migrations in JS. It has the same model as golang-migrate, and isn't covered in depth here.

## Team conventions

A tool can't enforce discipline for you. These conventions matter more than which tool you pick:

- **One migration, one transaction**: a migration either takes effect completely or doesn't appear in the database at all. Flyway and golang-migrate wrap a single migration in a transaction by default. The exception is statements like `CREATE INDEX CONCURRENTLY`, which can't run inside a transaction block — either split it into a separate migration file and confirm the tool's configuration allows skipping the transaction, or accept a locking index build.
- **Never modify a merged migration**: other environments may have already run it, so changing the file content means the version record no longer matches. If you made a mistake, **add** a corrective migration. This is just like fixing already-released code by writing a new commit rather than rewriting history.
- **Idempotency has limits**: `CREATE TABLE IF NOT EXISTS` prevents a "table already exists" error, but if the table exists with a different structure it passes silently and hides schema drift. `ADD COLUMN IF NOT EXISTS` is usable, but there's no equivalent for changing a column type or a constraint. `IF NOT EXISTS` is meant for "a backstop in case something was created manually" scenarios — don't treat it as a normal technique. Bypassing the tool to hand-edit production structure is the number one cause of a broken migration system.

Locking and long-transaction risk during migration execution: see [locks and concurrency bottlenecks](../performance/lock-and-concurrency-bottlenecks). For the mechanisms behind constraints and indexes: see [lock system](../internals/lock-system).
