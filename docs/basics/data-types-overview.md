# 数据类型总览

PostgreSQL 的类型系统是它区别于许多数据库的地方：内置类型覆盖数值、字符、时间、布尔、二进制、UUID、网络地址等，还允许用户自定义类型。本文梳理业务建表最常用的几类，以及 `serial` 与 `GENERATED ... AS IDENTITY` 的取舍。每种类型的完整规格见官方 [Data Types](https://www.postgresql.org/docs/current/datatype.html) 一章；JSONB、数组、range 等特色类型见 [特色类型概览](./special-types-intro)。

## 数值类型

| 类型 | 存储 | 范围 / 精度 | 典型用途 |
| --- | --- | --- | --- |
| `smallint` | 2 字节 | -32768 ~ 32767 | 状态码、枚举值 |
| `integer` / `int` | 4 字节 | 约 ±21 亿 | 一般整数计数 |
| `bigint` | 8 字节 | 约 ±9.2×10^18 | 大表主键、分布式 ID |
| `numeric(p,s)` | 变长 | 精确到任意精度 | 金额、费率等精确计算 |
| `real` | 4 字节 | 6 位十进制精度 | 科学计算、近似值 |
| `double precision` | 8 字节 | 15 位十进制精度 | 近似值、统计量 |

```sql
CREATE TABLE num_demo (
    qty      integer      NOT NULL,
    price    numeric(10,2) NOT NULL,   -- 精确两位小数
    ratio    double precision,
    CONSTRAINT qty_positive CHECK (qty > 0)
);

INSERT INTO num_demo VALUES (3, 19.99, 0.375);

-- 注意浮点类型不做精确比较
SELECT 0.1::double precision + 0.2::double precision = 0.3;  -- f
SELECT 0.1::numeric(10,1) + 0.2::numeric(10,1) = 0.3;        -- t
```

两条选型规则：

- **金额、汇率、库存等需要精确十进制的列用 `numeric`**。`float`/`double` 采用 IEEE 754 二进制浮点，`0.1 + 0.2 != 0.3`，做对账必然出问题。`numeric` 运算更慢，但正确性优先。
- **主键与外键用 `bigint`**。`int` 的 21 亿上限在流水表、日志表上并不遥远，回改列类型要重写整张表。金额设计的更多细节见 [金额与数值](../database-design/money-and-numeric)。

## 字符类型

```sql
CREATE TABLE char_demo (
    code3   char(3),        -- 定长，不足补空格
    name    varchar(64),    -- 变长，超过 64 字符报错
    bio     text            -- 变长，不限长
);
```

- `char(n)` 定长，插入短值自动补空格，比较时尾随空格也被忽略——语义容易踩坑，除非对接固定宽度协议，否则不用；
- `varchar(n)` 变长，n 是**字符数**上限而非字节数；
- `text` 变长且不限长，PG 中 `varchar` 与 `text` 底层存储完全相同，性能没有差异。

**首选 `text`，需要限长时加 `CHECK (char_length(bio) <= 500)`**。好处是后期改限制只需改 CHECK 约束（或干脆去掉），不用像 `varchar(64)` 改成 `varchar(128)` 那样做整列重写。PG 的这一行为与 MySQL 不同：在 MySQL 里 `varchar` 与 `text` 的行存储与索引行为有明显差别，迁到 PG 后不必保留旧习惯。

## 时间类型

| 类型 | 说明 |
| --- | --- |
| `date` | 只有日期（年月日） |
| `time [without time zone]` | 一天中的时刻 |
| `time with time zone` | 带时区偏移的时刻，少用 |
| `timestamp` | 不带时区的时间戳 |
| `timestamptz` | 带时区的时间戳 |
| `interval` | 时间长度，如 `3 days 02:30:00` |

```sql
CREATE TABLE time_demo (
    happened_at  timestamptz NOT NULL DEFAULT now(),
    birthday     date,
    duration     interval
);

INSERT INTO time_demo (birthday, duration) VALUES ('1995-06-01', '90 minutes');

SELECT happened_at AT TIME ZONE 'Asia/Shanghai' FROM time_demo;  -- 按时区取本地时间
SELECT now() + interval '7 days';                                -- 时间运算
```

`timestamptz` 的实现要点：**存储时统一转成 UTC**，显示时按会话 `TimeZone` 设置渲染。因此"列里到底存了什么时区"不会错乱，只有显示会变。存用户本地时间且不关心时区的场景（如生日）用 `date` 或 `timestamp` 更贴切。时间建模的完整讨论见 [时间建模](../database-design/time-modeling)。

## 布尔、UUID 与二进制

```sql
CREATE TABLE misc_demo (
    is_active   boolean NOT NULL DEFAULT true,
    external_id uuid    NOT NULL DEFAULT gen_random_uuid(),
    payload     bytea
);

INSERT INTO misc_demo (payload) VALUES (decode('48656c6c6f', 'hex'));

SELECT is_active FROM misc_demo;                    -- t / f
SELECT external_id FROM misc_demo;                  -- e0a1b2c3-...
SELECT octet_length(payload) FROM misc_demo;        -- 5
```

- `boolean` 取 `true` / `false` / `NULL` 三态，输出常显示为 `t` / `f`；
- `uuid` 用 16 字节存 UUID，比 `text` 存 UUID 省空间且可直接比较；PG 13 起内置 `gen_random_uuid()`（基于 `pgcrypto` 的旧写法不再需要）；
- `bytea` 存任意二进制（图片、加密块），大对象走 TOAST 机制，见 [TOAST 与大字段](../internals/toast)。

## serial 与 GENERATED ... AS IDENTITY

自增主键有两种写法：

```sql
-- 旧写法：serial 是伪类型，背后创建并挂接一个序列
CREATE TABLE orders_old (
    id serial PRIMARY KEY,
    note text
);

-- 推荐写法：PG 10 起的标准 SQL 语法
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    note text
);

INSERT INTO orders (note) VALUES ('a') RETURNING id;
--  id
-- ----
--   1
```

`serial` 的问题：它只是语法糖，实际创建了一个独立的 sequence 对象，列与序列之间的依赖关系记录松散——`pg_dump` 在复杂场景下可能丢失默认值关联，改 owner、迁移表时也容易把序列留下或丢掉。`GENERATED ... AS IDENTITY` 是 SQL 标准语法（PG 10 起，见 [CREATE TABLE](https://www.postgresql.org/docs/current/sql-createtable.html) 的 identity 子句），把序列作为列的附属物管理：

- `GENERATED ALWAYS AS IDENTITY`：默认拒绝手动插 id，要显式覆盖需写 `OVERRIDING SYSTEM VALUE`，防止应用乱插主键；
- `GENERATED BY DEFAULT AS IDENTITY`：行为接近 `serial`，允许手动指定值；
- `ALTER TABLE orders ALTER COLUMN id RESTART WITH 1000;` 直接重置计数，不必去操作序列对象。

旧表里的 `serial` 不必急于迁移，但新表建议统一 identity 写法。主键选型（identity vs UUID）的深入对比见 [主键设计](../database-design/primary-key-design)。

## 类型别名

PG 保留了一批 SQL 标准与历史别名，`pg_catalog` 里看到 `int4`、`varchar` 等名字不要奇怪：

| 你写的 | 系统里的真名 | 备注 |
| --- | --- | --- |
| `int` / `integer` | `int4` | 内部编号 4 表示 4 字节 |
| `bigint` | `int8` | 8 字节 |
| `smallint` | `int2` | 2 字节 |
| `real` | `float4` | 4 字节浮点 |
| `double precision` | `float8` | 8 字节浮点 |
| `varchar(n)` | `character varying(n)` | 同一类型 |
| `timestamptz` | `timestamp with time zone` | 同一类型 |

别名只影响书写，不影响存储与行为；查系统目录（`pg_attribute`、`\d 表名`）时看到的是真名。

## 注意事项与常见坑

- **`numeric` 没有精度上限但也别滥用**：`numeric` 参与大量运算会比整数慢，计数器、自增 id 用整数族；
- **`timestamp` 与 `timestamptz` 混用**会让跨时区数据错乱，业务表统一 `timestamptz` 是更省心的默认；
- **`char(n)` 的补空格行为**在 `WHERE code3 = 'AB'` 这类比较里会"看起来相等"，容易掩盖脏数据；
- **`money` 类型不建议**：区域设置影响输出、除法行为怪异，用 `numeric` 更可控；
- **改列类型可能锁表重写**：`int` 改 `bigint` 在 PG 里需要重写整表（`ALTER TYPE ... USING`），大表要先规划窗口期，见 [锁系统](../internals/lock-system)。
