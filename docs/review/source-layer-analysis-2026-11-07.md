## Architecture Layer Walkthrough

### 1. Content Layer — where the knowledge lives

- **Implementation files.** 136 prose pages across 11 topic directories plus 11 `index.md` section guides, the home page, and the knowledge map, all under `docs/` (counted by `docs/review/structure-audit-2026-10-19.md:11-24`). Representative paths: `docs/basics/what-is-postgresql.md:1`, `docs/internals/wal-mechanism.md:1`, `docs/security/pg-hba-and-authentication.md:1`, `docs/appendix/glossary.md:1`.
- **Configuration schema.** None. Content pages are plain Markdown; the only content-side config is the per-directory `index.md` convention and the H1/section-title mapping declared in `i18n-map.mjs:174` (`sections`).
- **Protocol file.** None. Content is consumed directly by the VitePress markdown pipeline; there is no wire protocol.
- **Copy location.** In-page prose is the copy. Shared copy strings (nav, sidebar, section titles) live in the navigation layer, not in content files.

### 2. Navigation / i18n Layer — single source of truth for labels and routes

- **Implementation files.** `docs/.vitepress/i18n-map.mjs` is the entire layer: `pages` at `i18n-map.mjs:5`, `sections` at `i18n-map.mjs:174`, `titles` derived at `i18n-map.mjs:185`. Builders are in `config.mts:8` (`buildNav`) and `config.mts:22` (`buildSidebar`).
- **Configuration schema.** No separate schema file. The registry *is* the schema: `pages` entries are `[slug, enTitle, zhTitle]`, `sections` entries are `[enTitle, zhTitle, collapsed]`. The header comment states "nothing else may hand-write section names or page titles" (`i18n-map.mjs:1-3`).
- **Protocol file.** None. `i18n-map.mjs` is imported by `config.mts:2`; no protocol exists because both sides are TypeScript/JavaScript modules in the same process.
- **Copy location.** All bilingual title strings live here (English title + Chinese title per slug), which is what makes the derived `titles` map possible.

### 3. Configuration Layer — VitePress site config and theme

- **Implementation files.** `docs/.vitepress/config.mts:44` (`defineConfig`), theme entry `docs/.vitepress/theme/index.ts:1`, readability CSS `docs/.vitepress/theme/custom.css:1`.
- **Configuration schema.** Inline in `config.mts`; it is the VitePress `UserConfig`. `package.json:16` overrides `vite` to `6.4.4` to clear audit warnings.
- **Protocol file.** None. Config is consumed by VitePress at build/dev time via the `docs/.vitepress` convention.
- **Copy location.** Locale-facing UI strings are inline in `config.mts:93-132` (`locales.root` / `locales.zh` theme config).

### 4. Delivery Layer — build and publish pipeline

- **Implementation files.** `.github/workflows/deploy-docs.yml:1`; build script `package.json:7` (`docs:build`), dev `package.json:6`, preview `package.json:8`.

- **Protocol file.** None. GitHub Pages protocol is implicit in `actions/deploy-pages@v5` and the `pages: write` permission (`:10`).
- **Copy location.** None; the workflow carries no user-facing text.

## Why the Layers Are Split This Way

1. **The repo is a static documentation site, not an application.** There is no backend, no database, and no runtime state; every "service" is a file consumed by the VitePress build (`package.json:7` `vitepress build docs`). This forces a document-centric layering: prose (content), metadata (navigation), config (theme/plugins), pipeline (CI). Evidence: `package.json:2`, `package.json:7`, `docs/.vitepress/config.mts:44`.

2. **Bilingual routing makes navigation a separate concern.** The site is English at root and Chinese under `/zh/` (`config.mts:61-76`). Both navs and both sidebars are derived from one registry (`i18n-map.mjs:5`, `:174`, `:185`), and the file's own comment forbids hand-writing section names elsewhere (`i18n-map.mjs:1-3`). If titles were scattered across content pages, the bilingual consistency contract would be unenforceable. Evidence: `i18n-map.mjs:1-5`, `config.mts:93-132`.

3. **Content and route lists must not drift.** The dead-link gate (`ignoreDeadLinks: false`, `config.mts:52`) fails the build on broken links, so the content layer is verified against the navigation layer at build time. The sidebar is declared authoritative (`README.md:60`), and the structure audit records 148 unique targets / 0 missing targets (`docs/review/structure-audit-2026-10-19.md:119-129`). Evidence: `config.mts:52`, `README.md:60`, `docs/review/structure-audit-2026-10-19.md:119-129`.

4. **Publishing is environment-bound, not authoring-bound.** The workflow needs `pages: write` / `id-token: write` permissions and the GitHub Pages environment (`deploy-docs.yml:8-11`, `:43-52`), none of which belong in content or config. Keeping it in `.github/workflows/` isolates the deployment surface from doc editing. Evidence: `deploy-docs.yml:8-15`, `:43-52`.

5. **State storage is filesystem-only, so no state layer exists.** The only persisted state is Markdown source (content) and the git-ignored build output (`docs/.vitepress/dist/`, `.gitignore:2`). There is no Redis, MySQL, in-memory store, or runtime daemon to layer around. The absence of a state layer is itself a structural fact to record. Evidence: `.gitignore:1-3`, `package.json:7`, `deploy-docs.yml:36`.
